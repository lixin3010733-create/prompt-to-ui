# 01 · 三层架构方法论

> 组件来自大厂开源规范，配图来自 Unsplash，布局与文案来自大模型。三者分工明确，AI 生成的界面才可复现、可交付。

## 一、为什么必须分层

大模型生成 UI 时出现的问题，几乎都能追溯到「某一层没有指定唯一来源」：

| 症状 | 根因 | 修法 |
|---|---|---|
| 每次生成长得不一样 | 组件层没锁定，模型自由发挥 | 指定一套组件规范，禁用规范外样式 |
| 视觉好看但没法还原成代码 | 生成的控件不属于任何组件库 | 用真实的 token（圆角 / 间距 / 字阶）约束 |
| 配图全是灰块或来源不明 | 图库层没接 | 指定图源与关键词，要求风格统一 |
| 文案假得刺眼、数据互相矛盾 | 大模型层缺少约束 | 给占位数据设定合理区间与自洽要求 |

## 二、三层各自的职责边界

### 第一层：组件（不可由模型创造）

按钮、输入框、卡片、标签、开关、底部导航等控件。

来源是大厂开源规范的**复刻封装**，不是实时拉取：

- Ant Design（蚂蚁集团）—— 后台、中台、复杂表单场景最全
- TDesign（腾讯）—— 国内业务语境，覆盖小程序与移动端
- Element UI / Element Plus（饿了么）—— Vue 生态常用
- Shadcn UI —— 代码即组件，适合直接进前端项目

关键是**提前把这些规范复刻成内部组件库**。AI 生成页面时被强制要求在这套库的视觉规格内搭建，好处有两个：控件样式天然统一；后续转前端代码时每个控件都能对上号。

> 组件本身的结构、圆角、阴影、配色规范来自大厂开源规范；工具方做的是复刻与封装，不是实时远程调用。

**模型在这一层的权限是：只能排列组合，不能凭空创造。**

### 第二层：图片素材（半可控）

接 Unsplash 的公开图片检索 API。提示词里写「户外山林、徒步风景」，AI 提取关键词、调用接口、拉取匹配的免费图片放进原型。

可控的部分：题材、氛围、大致色调、不要出现什么。
不可控的部分：具体是哪一张。

关于这一点有一层常见的误解，值得单独强调：

> Unsplash 图片免费可商用，但仅限于原型演示。正式上线项目最好二次核验版权。

### 第三层：布局与文案（完全交给模型）

这一层才是大模型真正的主场：

- **布局**：理解需求后决定页面分几块、卡片放哪、导航在底部还是顶部、信息层级怎么排
- **占位文案**：人名、路线名、里程、评分等假数据现场生成

这些数据不是从素材库调取的，是模型现编的 —— 所以**必须人工核对业务逻辑**，模型编的里程和耗时常常不自洽。

## 三、两个容易混为一谈的能力

| 能力 | 本质 | 类比 |
|---|---|---|
| 组件库 | 积木零件，规格来自大厂开源规范 | 乐高积木 |
| 图库（Unsplash） | 图片素材库 | 贴图纸 |
| 大模型 | 做布局、定信息层级、生成占位文案、理解产品需求 | 搭积木的人 |

三者缺一不可，但不能互相替代。只给模型不留组件库，得到的是每次不同的漂亮图片；只给组件库不用模型，那还是手工作业。

## 四、落地顺序

按这个顺序做，返工最少：

1. **先定组件规范** —— 选一个库，把 token（圆角、间距、字阶、色板）固化下来
2. **再定图源关键词** —— 写清楚题材、调性、禁止项（如「不要人脸特写」）
3. **最后写 Prompt** —— 把前两层作为参数传进去，只让模型决定布局与文案
4. **生成后校验** —— 控件是否越界、数据是否自洽、异常状态是否缺失
